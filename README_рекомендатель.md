# CatBoost-рекомендатель поставщиков

В проекте есть подготовка данных на pandas, CatBoostRanker, поисковый каталог кандидатов и FastAPI для подключения вашего сайта. API принимает текст закупки, находит кандидатов в каталоге и ранжирует их моделью. `rank_score` — относительный балл ранжирования, не вероятность победы.

Подробное объяснение данных, признаков, связей, метрик и особенностей решения — в [ОБЪЯСНЕНИЕ_МОДЕЛИ.md](ОБЪЯСНЕНИЕ_МОДЕЛИ.md).

Модель учится только на электронном магазине (ЭМ): там есть и победители, и проигравшие. В АИС ГЗ все строки помечены победителями, поэтому его записи полезны для поиска компаний и их специализации, но не подходят для обучения конкурентному ранжированию.

## Подготовить выборку и профили

Нужен Python 3.11+ и зависимости из `requirements.txt`.

```bash
python -m pip install -r requirements.txt
python prepare_catboost_data.py
```

Скрипт обрабатывает CSV через pandas в четыре шага:

1. Отбрасывает некорректные ИНН и повторные пары «лот–поставщик».
2. Склеивает закупку, её предмет и участников по `lot_id`. Для обучения отбирает ЭМ; АИС ГЗ сохраняет в каталоге кандидатов.
3. Сводит коды ТРУ до основного раздела ОКПД2 для лота.
4. Для каждой закупки строит признаки только из более ранних закупок. Победа из текущего или будущего не просачивается в признаки.

Готовая таблица сохраняется в `prepared/training_features.csv.gz`; профили конкурентных результатов ЭМ и поисковый каталог из обоих каналов — в `artifacts/`. Таблица для обучения содержит только метку, идентификаторы, дату и признаки модели; лишние текстовые и объяснительные колонки в неё больше не записываются. В каталоге около 90 тысяч связей «поставщик — раздел ОКПД2» и до четырёх недавних описаний закупок для каждой связи. Названий компаний в исходных CSV нет: сайт может показать ИНН или дополнить название из проверенного источника.

## Признаки простыми словами

| Признак или сигнал | Простое объяснение | В CatBoost |
| --- | --- | --- |
| `history_participations`, `history_wins` | Сколько раз поставщик участвовал и выиграл раньше. | Да |
| `history_win_rate` | Сглаженная доля побед; без истории нейтральна — 0.5. | Да |
| `history_rate_confidence` | Надёжность процента: `участия / (участия + 10)`. | Только объяснение в API |
| `days_since_supplier_activity` | Дней с последнего участия; без даты — 3650. | Да |
| `category_participations`, `category_wins`, `category_win_rate` | Опыт и победы в основном разделе ОКПД2 закупки. Доля сглажена. | Да |
| `category_rate_confidence` | Надёжность доли побед в категории: `участия / (участия + 5)`. | Только объяснение в API |
| `category_code_match` | В обучении: поставщик раньше участвовал в этом разделе ОКПД2. При запросе к API: его заявленный раздел совпадает с закупкой. Это приближённое соответствие, особенно для новых компаний. | Да |
| `days_since_category_activity` | Дней с последней активности в категории. | Да |
| `buyer_participations`, `buyer_wins`, `buyer_win_rate` | Опыт поставщика у этого заказчика. | Да |
| `buyer_category_wins` | Сколько раз поставщик раньше побеждал у этого заказчика именно в нужном разделе ОКПД2. | Да |
| `buyer_rate_confidence` | Надёжность доли побед у этого заказчика. | Только объяснение в API |
| `text_similarity` | Лучшее сходство с последней победой компании вообще и последней победой в нужной категории. Без истории — с переданным профилем. Формы вроде «медицинские» и «медицинских» приводятся к одной основе, общие слова вроде «поставка» пропускаются. | Да |
| `start_price_log` | Размер закупки в сжатом масштабе. Для ЭМ значения выше 600 тыс. ₽ ограничены в модели: в ремонте встречаются огромные суммы единичных расценок. Исходный CSV сохраняется без изменений. | Да |
| `category_division` | Основной раздел ОКПД2 закупки. | Да |
| `category_count` | Сколько разных разделов ОКПД2 есть в лоте. | Да |

Уверенность — не второй процент побед, а оценка объёма данных, на котором он основан. Например, 1 победа из 1 участия слабее подтверждена, чем 20 из 25. В проверке CatBoost эти три отдельные уверенности не улучшили качество сверх счётчиков и сглаженных долей, поэтому показываем их в объяснении, но не даём модели лишний дублирующий сигнал. Давность общей активности, напротив, дала модели дополнительную информацию.

## Обучить CatBoost

```bash
python train_catboost.py
```

По умолчанию обучение идёт на закупках ЭМ до 2025-01-01, а проверка — на ЭМ 2025 года. Ранжировщик использует `YetiRankPairwise`, группирует строки по лоту, применяет early stopping и сохраняет:

- `artifacts/supplier_ranker.cbm` — CatBoost-модель;
- `artifacts/training_report.json` — метрики и граница дат;
- `artifacts/feature_importance.csv` — важность признаков.

В 10% обучающих лотов история поставщиков скрывается, чтобы смоделировать cold start: модель получает раздел категории и совпадение текста профиля с закупкой, а счётчики истории обнуляются и доли становятся нейтральными. Метрика cold start — симуляция среди уже известных компаний; её ещё надо проверить на реальных новых компаниях.

Проверка на 79 045 лотах 2025 года: Hit@1 = **65,44%** против **60,52%** у простого правила. Предыдущая модель: 65,48%. При скрытой истории результат вырос **37,52% → 39,15%**; прирост есть во всех четырёх кварталах 2025 года. Это измеренное улучшение при недостатке истории при почти прежнем обычном качестве. Число признаков осталось **17**, число деревьев уменьшилось **683 → 291**. Сравнили один и два текстовых признака; оставили один, поскольку второй почти не добавил пользы. Результаты вариантов сохранены в `artifacts/model_comparison.json`.

2025 год используется для early stopping и выбора варианта, поэтому это validation, а не независимый финальный тест. Метрики относятся к записанным участникам лота; качество поиска по всему рынку отдельно ещё не измерено.

## Подключить сайт

Запустить API из этой папки:

```bash
uvicorn site_api:app --host 0.0.0.0 --port 8000
```

`GET /health` проверяет наличие модели и профилей. `POST /recommend` принимает описание закупки, коды ОКПД2, заказчика и список кандидатов. Кандидаты могут быть историческими или добавленными из внешнего пула.

Если сайт пока не имеет собственного списка кандидатов, он может вызывать `POST /search` с одной поисковой строкой. API выделяет из неё текст предмета, код ОКПД2 и ИНН, ищет в локальном каталоге до 300 кандидатов и передаёт их CatBoost. Для запросов из двух и более содержательных слов нужно совпадение минимум двух слов: так «медицинские изделия» не совпадут с «изделиями из фарфора». При известном коде ОКПД2 лучше указывать его: автоматическое определение раздела по словам может ошибиться.

```json
{"query":"ремонт автоэвакуаторов","okpd2_code":"45.20.21","top_k":10}
```

Одна строка может содержать всё сразу:

```json
{"query":"ремонт автоэвакуатора ОКПД2 45.20.2 ИНН заказчика 7842019044"}
```

Также работают `{"query":"45.20.2"}` для просмотра раздела и `{"query":"ИНН 7805198740"}` для поиска конкретного поставщика. ИНН без пояснения означает **ИНН поставщика**. Для персонализации выдачи пишите **«ИНН заказчика»**; для явного поиска компании — **«ИНН поставщика»**. Если текст и ИНН поставщика указаны вместе, API показывает точное совпадение по ИНН с данными о его опыте, а не рейтинг из нескольких компаний. В этом режиме `rank_score` равен `null`. Ответ содержит `parsed_query` (как строка была понята) и `mode`: `recommendations`, `category_browse` или `supplier_lookup`.

Код `45.20.2` сохраняется в `parsed_query` полностью, но текущий каталог кандидатов сгруппирован по первым двум цифрам (`45`). Поэтому точный код помогает выбрать раздел, а поиск по более узкой подкатегории пока опирается на слова описания.

`POST /recommend` нужен, когда сайт уже собрал собственный список компаний и хочет только ранжирование:

```json
{
  "purchase_text": "Поставка медицинских изделий",
  "okpd2_codes": ["32.50.13.110", "32.50.50.190"],
  "customer_inn": "7800000000",
  "start_price": 1000000,
  "top_k": 20,
  "candidates": [
    {
      "supplier_inn": "7700000000",
      "supplier_name": "Поставщик",
      "okpd2_codes": ["32.50.13.110"],
      "profile_text": "Медицинские изделия и оборудование",
      "source": "Реестр",
      "source_url": "https://example.org/company"
    }
  ]
}
```

`POST /search` работает только с локальным сохранённым каталогом и не делает сетевых запросов во время поиска. Для нового поставщика без истории нужны его ИНН и описание товаров или услуг; коды ОКВЭД нельзя подставлять как коды ОКПД2.

API возвращает относительный CatBoost `rank_score` и `quality_signals`: совпадение раздела, сходство текста, объём исторических данных и давность активности. Этот балл не является вероятностью победы. Статус поставщика, количество предложений и совпадение региона/категории из внешнего каталога принимаются API и выводятся в объяснении результата, но пока не влияют на CatBoost-оценку: в исторической обучающей выборке нет таких полей. При чтении `external_supplier_pool.csv` поле `okpd2_codes` нужно разобрать из JSON-строки в список, а `portal_offer_count` — в число.

## Ограничения текущей версии

- Обучающая разметка ЭМ содержит победителей и проигравших в выгрузке, а не всех поставщиков рынка. Неизвестно, включает ли она всех подававших заявки или только допущенных. Метрика на 2025 год проверяет ранжирование только среди записанных участников.
- Раздел ОКПД2 для лота выбирается по наиболее частому коду ТРУ; многоотраслевые лоты упрощаются до одного основного раздела.
- Текстовое сходство — пересечение слов без лемматизации; модель не использует внешние API нейросетей.
- После добавления реального пула компаний нужно отдельно оценить покрытие кандидатов и качество рекомендаций для поставщиков без истории.

## Внешний пул поставщиков из Портала поставщиков

`artifacts/external_supplier_pool.csv` содержит точечное дополнение для рыбной продукции: ООО «ПУР-РЫБА» с подтверждёнными предложениями и регионом поставки Санкт-Петербург. ИНН проверен на отсутствие в исходной истории поставщиков 2024–2025.

Эта строка предназначена для пула кандидатов, а не для обучения: `history_status` явно помечает отсутствие истории. В `okpd2_codes` указаны широкие разделы `["03", "10"]`: среди предложений есть рыба и переработанные рыбные продукты, включая консервы; для консервов код раздела 10 подтверждается названиями и кодами ТРУ в исходном датасете. Категории каталога Портала (СТЕ) не выдаются за точный код ОКПД2 товара. `POST /search` добавляет запись при совпадении раздела и слов закупки. При отправке CSV в `/recommend` поле `okpd2_codes` нужно разобрать из JSON-строки в список.
